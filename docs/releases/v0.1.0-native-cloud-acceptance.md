# Native Cloud acceptance for v0.1.0

This is an operator checklist for the installed macOS app. It does not enable Cloud or perform any action. The local Rust, component, HTTP mock and Stripe fixture tests remain useful regression evidence, but they do not establish hosted authentication, real Keychain persistence or paid fulfillment.

The current production pins are intentionally unconfigured. Until the private cutover and launch prerequisites have passed, record hosted steps as **blocked**, not passed. Do not change an isolation flag, reuse the active staging project or substitute a browser fixture to close this checklist.

## Authority and isolation before execution

Record the reviewed app commit and private service commit, device architecture, app version, exact bundle path, full executable path/PID and intended environment. Verify the app signature and that its binary matches the reviewed build. A version label or bundle identifier alone does not identify the running code. Preserve the user's installed app, local work and selected approval mode.

Use a dedicated macOS test user for remembered **production** session acceptance, or stop until an equally strong isolation arrangement has been reviewed. A different app name, bundle identifier or `GYRO_TEST_DATA_DIR` does **not** by itself isolate the production Cloud Keychain entry. Production refresh storage is keyed by service `dev.gyro.cloud.refresh` and environment/project; it is not keyed by the local data directory. Never inspect, export or delete the owner's remembered credential to make a test pass.

For staging acceptance, use the reviewed separate staging bundle and its persistent launcher/data profile. Verify its Auth project and Keychain scope. Staging results cannot close production acceptance. After quitting, select the exact controlled bundle again: UI automation may reopen an app without process-only test variables. Confirm the process path, data profile and IPC owner after every restart; stop if the normal user app or wrong profile was selected.

Keep the evidence directory private. Do not record email addresses, sign-in links/codes, JWTs, refresh credentials, payment URLs, payment details, database URLs or secret values. Record safe statuses, timestamps, boolean assertions, version/commit identities and sanitized error codes. Existing provider connections and local chat titles are private data too.

The following actions require separate, specific approval before their step starts:

- Sending a sign-in email or entering an authentication proof for the named test account.
- Creating or modifying hosted test accounts, sessions, devices, subscriptions or other retained data.
- Submitting a live charge, refund, cancellation or plan change. Specify the account, merchant, plan, currency/amount and exact operation; the owner completes any required payment handoff.
- Running a paid provider request. Specify positive limits for call count and maximum spend first; no approval means zero paid calls.
- Production provisioning, migration, deployment, key/credential changes or environment enablement.

Running a local mock, opening Settings or preparing this checklist grants none of those approvals. Do not repeat an email, checkout or paid request because a response is slow or ambiguous; inspect the existing operation/status first.

## Payment evidence and live-mode testing

Payment lifecycle simulations belong in the Stripe sandbox. Stripe prohibits live-mode tests using real payment method details; do not ask the owner to fund a test subscription/refund in production. P01/P02 below must be executed in the approved sandbox for prelaunch financial acceptance. Use production configuration, signature and account/session checks for the live environment, then monitor the first **genuine** customer purchase after opening checkout. Record its invoice/fulfillment observations separately; do not report a sandbox payment as a production payment or require a fabricated live transaction before any genuine customer can subscribe. [Stripe testing rules](https://docs.stripe.com/testing).

The separately approved synthetic provider-adapter request passed on 5 November. It did not execute P04 through an installed app and hosted account/quota service. Its single-call authority is exhausted; do not repeat it or silently reuse its budget for another request. Complete remaining native/session checks using the approved environment and identity, preserving the user's app and production Keychain scope.

## Existing checks and their limits

`scripts/check-cloud-connection-wire.mjs` exercises the Rust coordinator against a disposable local HTTP simulator. It does not launch native UI, use macOS Keychain, send email or reach the hosted service. The `cloud_connection` Rust tests include injected-store rotation, restore, stale-response and sign-out regressions; a test store is not an OS Keychain acceptance result. The packaged browser/LSP smoke checks likewise do not verify a Cloud subscription.

Permissions already disclose provider-dependent workspace/network boundaries and the effect of Full access; do not change the user's mode during acceptance. The macOS notification page already distinguishes a denied OS permission and directs the user to System Settings. Record blocked notifications separately and leave the OS decision unchanged; it is not proof that Cloud or the app's security controls failed.

## Isolated real Keychain mechanism check

On macOS, `pnpm smoke:keychain` runs an explicit debug-only Rust example with `Cargo.lock` enforced. It uses eight fresh child processes and one random `acceptance-only` Keychain account containing synthetic, non-authenticating values. It verifies first absence, save, cross-process load, rotation, post-restart load, cross-project write rejection, deletion and final absence. Stored access tokens are rejected. Each child, including cleanup, has a 20-second deadline; a blocked process is killed and reaped. Cleanup targets only that synthetic account. The factory cannot address the production or staging account names; it is compiled out of release builds and is not a webview command.

This check passed on the arm64 verification Mac on 4 November 2026, with 16 Supabase adapter/unit checks also passing. It closes the real OS storage/restart mechanism gap only. It sends no email, authenticates nobody, accesses no owner credential and spends nothing. Hosted sign-in, real refresh-token rotation/revocation, the app's remembered-session UX and billing/provider fulfillment still require the separate N/P acceptance steps above. CI runs the same explicitly isolated mechanism check on its macOS runner; ordinary unit tests still never touch real Keychain entries.
