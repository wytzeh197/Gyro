# Gyro v0.1.6 product quality plan

**Goal.** Make Gyro dependable and responsive across its existing features and tools, and increase the share of real tasks that models finish correctly. Start with the browser because users are already encountering friction there. Apply the same standard to the rest of the product.

**Baseline.** Compare the installed v0.1.5 release with the exact packaged v0.1.6 candidate. Browser friction is reported and still needs a reproducible baseline. Record the app build, Mac and macOS version, provider runtime, model and effort, and the starting fixture revision for each run. This document proposes work and acceptance criteria. Results go in the release evidence as they are collected. [Previous release notes](../releases/v0.1.5.md)

## 1. Inventory the product and establish coverage

Use the app's visible features, CLI commands, and tool manifests as the inventory. Expand each row below into individual checks and record where each capability is available. For a model-facing tool, test whether the model can discover it, supply valid arguments, receive the expected result, and use that result to advance the task. For user-facing features, exercise the primary flow, a realistic failure, and recovery through the normal UI or CLI.

| Area | Required scenarios and observable results |
| --- | --- |
| Install, update, setup, and settings | Clean launch and provider setup. Upgrade from v0.1.5 with sessions, configuration, drafts, and provider access intact. Simulate a failed settings save and verify that the user can retry with their edits preserved. |
| Chat, composer, and sessions | Start, stream, queue, stop, retry, reopen, and resume. Cover attachments, dictation, split chats, and long histories. Verify ordering, draft retention, final status, and that retries do not duplicate sends or side effects. |
| CLI and workspace continuity | Resume the same task between desktop and CLI with its thread, workspace, branch, approvals, and changed files intact. Exercise stale or mismatched workspace context and ensure actions stay scoped to the selected target. |
| Provider connections, tools, and usage | Cover sign-in or connection, model selection, tool availability, streaming, cancellation, and usage displays. Exercise a representative subscription CLI, API, and local model route, then cover advertised differences on other supported routes. Test invalid auth, unavailable capabilities, quota and timeouts. Verify truthful errors and usage where measurable. |
| Browser, web fetch, and App Preview | Exercise open, navigation, read, find, click, type, capture, annotations, viewport changes, user takeover, and retry. Cover web fetch and native-preview limitations through their own entry points. Follow the browser work below. |
| Editor, files, search, and code intelligence | Open, search, edit, save, rename, and recover. Verify file scopes across project roots, definitions and references, editor responsiveness on large files, and conflict handling when disk changes under an unsaved buffer. |
| Terminal, Run, Test, and problems | Run a command and a project test, stop a long-running command, inspect errors, and reopen output. Exercise failure, long output, Unicode paste, and typing during heavy output. Verify that exit status and linked diagnostics match the actual process. |
| Git, GitHub, diffs, and worktrees | Review the current changes, switch contexts, and inspect PR or Actions data. Test a stale diff, rejected mutation, dirty worktree, and unavailable GitHub access. Verify correct repo and branch targeting and that rejected actions leave the checkout unchanged. |
| Goals, Plan, approvals, Check, and Review | Verify plan-to-implementation, scoped approval, rejection, stop, and independent evidence. Exercise a changed revision between review and execution. Check and Review identify stale or missing evidence and surface unresolved findings. |
| Canvas and project memory | Open or create a relevant artifact, revise it, and reopen it. Confirm the current revision is visible and the user's draft survives. Verify that memory is scoped to the intended project and can be corrected or removed. |
| Workflows, automations, Code Mode, and delegation | Run the advertised execution paths with disposable inputs. Exercise pause, stop, restart recovery, duplicate-run prevention, fresh approval on reuse, execution limits, and truthful receipts. Verify that delegated results reach the correct session. |
| Remote access and Cloud states | Test remote connect, reconnect, terminal and draft recovery within supported configurations. Use two devices for sync and sleep/wake claims. Verify the states shown in the default Cloud configuration. Record separate evidence for experimental or hardware-dependent capabilities. |
| Desktop controls and accessibility | Verify keyboard access and focus through core flows, panel switching, menu-bar status, and approval and completion notifications. Exercise a narrow window and confirm recovery actions are reachable without a pointer where supported. |

For each case record the expected result, build and environment, evidence level, pass or fail, and linked follow-up. Use `blocked` for a missing runtime, account, or device, and `not applicable` only when the capability is outside that configuration's documented contract. Include failure counts and coverage gaps in the release summary.

## 2. First workstream — make the browser reliable

Start with one small loopback site, one JavaScript-heavy test page, and a repeatable navigation failure. Run the installed-app flow manually and through a supported live model. Keep the original site and viewport when investigating a reported failure. Use a minimal reproduction to make the resulting fix repeatable.

| Order | Scenario | Acceptance |
| --- | --- | --- |
| 1 | Open and navigate | The requested page renders and reports the correct URL and page identity, including after redirects, reload, back, and forward. A failed load exposes the failure and an effective retry. |
| 2 | Read and find | Targeted reads find visible controls and their labels. Results distinguish fresh content, truncated observations, and stale references. The model can recover by observing the current page. |
| 3 | Click, type, and verify | Pointer and keyboard actions reach the intended control. Re-observing confirms the actual page change. Disabled or protected controls, invalid refs, and unsupported interaction modes return accurate results. |
| 4 | Switch between model and user | The agent can work in the background, and revealing the browser gives the user the same page at the same state. Resizing and changing the viewport preserve correct input coordinates. Switching chats keeps their browser state separate. |
| 5 | Capture and annotate | Screenshots match the active page and viewport. An annotation carries the target, URL, viewport, and before image into the right composer. The model receives the expected evidence on image-capable routes, with clear feedback when capture or delivery fails. |
| 6 | Recover under contention | Slow or unresponsive pages, stale captures, cancellation, and concurrent chat activity leave the user able to retry or take over. A failed action does not report success or affect another session. |
| 7 | Complete the browser bug task | At a recorded mobile viewport, reproduce a menu that fails to open. Inspect or annotate the target, review and approve the fix, and verify that the menu opens, closes with Escape, restores focus, and still works at desktop width. Save before and after evidence from the matching viewport and revision. |

Triaging a browser failure starts with where it occurred. Compare the same operation manually and through the model, then inspect page identity, tool arguments, queue time, WebKit execution, and the resulting UI state. That separates model tool selection and stale-reference mistakes from browser execution and UI routing failures. Add a regression at the lowest layer that reproduces the cause, then rerun the installed workflow.

Reuse `pnpm test:browser-agent`, `pnpm test:browser-annotations`, `pnpm test:browser-event-routing`, and the macOS `pnpm test:browser-events-native` harness as appropriate. Record packaged-app acceptance separately from debug/native harness results. ## 3. Measure and improve product performance

Use the same Mac, OS, fixture, and starting state for each comparison. Separate cold and warm runs. Alternate build order where practical and keep fixture-based measurements separate from variable network and provider timings. Record sample counts, median and worst observed values, and p95 when the sample supports it. Keep timeouts and hangs in the record. Use the baseline's run-to-run variation to set regression budgets before comparing the candidate.

| Journey | Measure | Stress case |
| --- | --- | --- |
| Launch and resume | Launch to usable UI, project and chat open time, long-session resume time | Large saved history, multiple projects, cold start after restart |
| Live chat | Send to first useful activity, event receipt to render opportunity, interaction latency while streaming, stop to settled | Long response, attachment, concurrent sessions, large history |
| Workspace | Time to open project, search, read files, show Git status and diff, and switch panels | Large repo and diff, language server indexing, concurrent file edits |
| Terminal and tasks | Time to first output, typing responsiveness, completion and cancellation latency | High-volume output, large paste, test run alongside a model turn |
| Browser and tool execution | Open to usable page, read/find and click to verified state, screenshot latency, tool failure and retry counts | Script-heavy page, background browser, slow navigation, multiple sessions |
| Resource use and recovery | Gyro process-tree CPU and memory, UI stalls, memory after close, time to regain a usable state | Extended mixed workload with chat, editor, terminal, and browser open, followed by closing and reopening them |

Use the existing opt-in diagnostics to distinguish Gyro work, tool execution, provider latency, and approval wait. Report end-to-end time alongside the component timings. Prioritize repeatable stalls and regressions with the largest user-visible impact, then add a focused guard or repeatable run for each repair. ## 4. Evaluate real model outcomes

Start with three matched tasks. Use disposable repos with known starting revisions, fixed prompts, and acceptance checks prepared before the run. Keep the provider route, model ID, effort, approval mode, permissions, and user-input policy fixed within a pair. Record the provider CLI version and model revision when exposed. Repeat matched cases in fresh sessions, and include deliberately resumed sessions where the scenario requires them. Run live cohorts within an agreed request and spend cap for the configured route.

| Task | Independent success criteria |
| --- | --- |
| Browser bug | Reproduce the broken mobile menu, make the fix, and verify behavior in the actual browser at the original viewport. Pointer and keyboard assertions pass, and the desktop menu stays usable. |
| Multi-file fix | Repair a small defect that requires finding unfamiliar code, editing across files, and running tests. The intended assertions pass, the final diff stays in scope, and an unrelated failure remains visible if one is present. |
| Interrupted task | Stop and resume after partial progress or a failed tool call. Recover the requirements, workspace, changed files, and next action. Finish successfully without reapplying an earlier change or using stale evidence. Include desktop-to-CLI resume on a supported route. |

Report **verified completion rate** as passed runs divided by started runs, with failed and timed-out runs included in the denominator. Report unavailable planned runs separately. Check the final files, test output, or observed browser behavior. A successful tool call or a model's completion message is insufficient evidence of task success. For every run also record elapsed time, tool failures and retries, repeated reads, required user interventions, approval or scope violations, and observed usage where available.

When a task fails, assign the earliest evidenced cause and retain any contributing cause. Typical categories are model reasoning or tool selection, tool unavailable or incorrect, provider transport, context loss, unusable result handoff, and verification failure. Rerun the smallest reproduction after a fix and repeat the full matched task. Publish sample counts by route and task. Treat small cohorts as directional and apply the existing efficiency qualification gates to any proposed cost-saving default. ## 5. Sequence the work and triage findings

1. **Establish v0.1.5 baselines.** Inventory all shipped capabilities and identify their primary acceptance paths. Run the first browser cases and a mixed-workload performance pass. Prepare the three model tasks and their verifiers. Turn reproducible failures into backlog items.
2. **Fix browser fundamentals and cross-product blockers.** Work through navigation, observation, interaction, and recovery in that order where failures depend on one another. Fix data loss, incorrect mutations, and blocked common flows wherever they surface. Keep each repair tied to a repeatable scenario.
3. **Sweep remaining features and providers.** Run the rest of the coverage matrix, including recovery paths and concurrent use. Close recurring workarounds and the largest measured bottlenecks. Compare the matched model runs after the underlying tools are stable enough to use.
4. **Accept the exact candidate.** Rerun the full core matrix and affected regressions, compare performance and model results with the recorded baseline, and complete packaged upgrade and install checks. Record remaining limitations with the conditions under which users encounter them.

| Priority | Criteria | Typical examples |
| --- | --- | --- |
| **P0 — release blocker** | Data loss, wrong target or unintended mutation, misleading success with serious consequences, hang, or a common core flow that cannot complete or recover | Edits land in the wrong repo, an upgrade loses a draft, the browser repeatedly cannot load usable pages, or Stop cannot stop a run. |
| **P1 — release target** | Frequent friction, repeated model failure on representative tasks, significant measured slowdowns, or recovery that requires a manual workaround | A normal click often needs a reload, terminal input lags while output streams, or a resumed run repeats completed work. |
| **P2 — follow-up** | Infrequent recoverable defects and polish with limited impact on completing the task | An unclear label that still leads to the correct action, or cosmetic inconsistencies in a secondary view. |

Each backlog item records a concise user impact, affected route and build, reproduction steps, observed evidence and frequency, expected behavior, and the acceptance check. Track cause, owner, and fix revision as they become known. A reported symptom may enter triage immediately. Mark it confirmed once there is a reproducible case or direct evidence.

## 6. Release acceptance

- [ ] Every shipped surface and exposed tool is represented in the acceptance inventory. Core paths pass on the packaged candidate. Remaining unsupported or blocked configurations have an explicit status and evidence gap.
- [ ] No open P0. Reviewed P1 exceptions have a documented impact, observed conditions, and workaround where one exists. Repeat confirmed browser failures on the candidate and record the outcome.
- [ ] Matched performance runs show no repeatable regression outside the budgets set from the baseline. Targeted improvements have before and after evidence under the workload that originally showed the problem.
- [ ] The three model task families have independent verification on the selected routes. The candidate preserves verified completion across the matched core runs, and a targeted tool or workflow fix removes a reproduced failure or workaround. Record all failures and accounting gaps.
- [ ] Source checks and affected browser and native suites pass. The exact packaged candidate passes clean launch, update from v0.1.5, and the applicable checks in the release runbook. [Release runbook](../release.md) · [Clean-machine path](../clean-machine-path.md)

Keep the final evidence with the release review. Include the candidate commit and artifact identity, environment, commands or manual steps, before and after results, and remaining coverage gaps. Use screenshots and redacted logs where they establish the outcome. Feature expansion should enter this milestone when it resolves an evidenced blocker or adds a missing step needed to complete an existing workflow.
