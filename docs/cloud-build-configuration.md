Production `environmentIsolationVerified` is now true, reflecting the completed private cutover and physical isolation evidence. Normal builds therefore use the fixed production Auth/API pins; server-side paid admission still controls checkout independently. The private service now records the approved clean production cutover and physical isolation as complete. Do not repeat the cutover or infer production session readiness from physical isolation alone. Publishing a paid launch still requires the remaining production acceptance and operating checks. No provisioning, data removal or deployment is implied by these files.

After separately approved production provisioning, copy only the reviewed public pins (API/share origins, production Auth project reference and publishable key, verified isolation flag and replacement staging project reference) into this file, commit them, and rebuild normally with `pnpm desktop:bundle`. No runtime endpoint input is accepted from a webview. Compile-time `GYRO_CLOUD_V2_*` pins remain available for explicit builds; a partial or mixed pin set fails closed. The active staging project is rejected by production adapters; the existing project remains reserved until the isolation gate is verified. Debug-only `GYRO_CLOUD_V2_STAGING_*` configuration uses separate native state and Keychain identities and is absent from release adapters.

Access credentials remain in native memory. Remembered refresh credentials use macOS Keychain under `dev.gyro.cloud.refresh`, separated by environment/project. Restoring a remembered session is explicit; startup never signs in or requests an email. Subscribe is the only path that can create a service account. Refresh rotates the refresh credential, rechecks the service snapshot and updates every account/billing/Cloud surface. Sign out fences older responses, clears native state/Keychain and attempts server plus issuer revocation; pending revocation is reported rather than silently treated as success. A verified Auth session alone never grants a subscription or allowance.

The legacy `gyro_cloud` in-memory login and staging API are no longer registered as installed-app commands. Historic previews are not production acceptance. Production restart, refresh, sign-out and fulfillment still need hosted end-to-end acceptance after deployment; local transport and native unit tests do not close that gate.

Use the [installed native Cloud acceptance checklist](releases/v0.1.0-native-cloud-acceptance.md) for the remaining authentication, Keychain, restart, refresh, revocation and paid-fulfillment gates. Preparing or running a local mock does not authorize email delivery, hosted mutations, charges or paid provider requests. A test data directory alone does not isolate the production Keychain entry; the checklist requires a separately controlled test user or an explicitly reviewed equivalent before remembered-session testing.

## Staging build during the project cutover

`config/cloud-staging.json` is the public staging build handoff. The staging builder reads this file instead of embedding a project reference in its source. After an approved staging move, replace it with the private service's reviewed `desktop-cloud-staging.public.json` export and update the reviewed replacement reference in `config/cloud-production.json`. Neither file contains credentials. Do not copy the production pins into the staging file.

Run `node scripts/build-cloud-staging-app.mjs` to build the separate debug-only staging app. It validates the public inputs before invoking build tools and uses `Cargo.lock` with `--locked`. Once production isolation is verified, stale staging pins that still point at the repurposed production project are rejected. Staging API/share origins must also remain separate from the configured production origins. The existing staging project stays usable while production remains disabled and the cutover has not occurred.

Every staging project has a separate macOS identity and local profile. The validated full `authProject` becomes `dev.gyro.desktop.cloudstaging.<full-reference>`; the product/window name is `Gyro Cloud Staging <first-eight-reference-characters>`. Data lives at `~/Library/Application Support/Gyro Cloud Staging/<full-reference>`, and attachment/browser-capture asset access is scoped to that exact folder. Existing unscoped staging data and other projects are neither imported nor changed. For example, replacement project `tpskieaxnzltdmpebdfz` builds `Gyro Cloud Staging tpskieax.app` and uses its full-reference subdirectory.

The bundle's C launcher embeds the validated project at compile time and uses the same minimum macOS deployment target as the app, rather than the build host's OS version. A Finder reopen reconstructs the same project-specific data environment from the macOS account home, discarding inherited endpoint/data-directory overrides. It walks directories with `openat`/`O_NOFOLLOW`, requires owner-controlled parents and private `0700` staging directories, and refuses symlinks, shared-writable/nonowned paths or malformed project references. It does not chmod or migrate an existing profile to make a launch succeed. Review an unsafe existing directory explicitly instead of redirecting the app into another profile. Normal Gyro production identity, profile and frontend components remain unchanged; native Cloud Keychain records also retain their existing environment/project separation.

`pnpm test:cloud` includes offline checks for missing/mixed pins, secret-key rejection, nonpublic origins and the replacement-project boundary. These checks do not provision staging or establish hosted acceptance. The standard sidebar still has no Cloud destination; Account and Cloud remain accessible through Settings.

The focused `node scripts/check-cloud-staging-build.mjs` check also verifies project-specific app identities and asset paths. On macOS it strictly compiles the C launcher and runs its real startup logic only through a disposable-home harness with executable lookup/exec intercepted. The harness checks Finder-style empty/inherited environments, preserved old-profile sentinels, malformed project rejection, symlinks, directory permissions and ownership. It never starts Gyro or accesses an existing user profile/Keychain. Other platforms report the macOS compiler portion as skipped. These checks establish build/launcher isolation; actual native sign-in, restart and hosted acceptance still require the separately controlled staging run.

## Personal and business subscriptions

Plan & billing requires an explicit personal/business use selection before a new checkout. The same native session coordinator carries that choice through sign-in and sends `customerUse` to the billing endpoint. The backend owns the distinct pinned price/product/tax-code profiles, checks payment ownership and amount, and keeps the selected category when a subscription changes plan at renewal. Changing the selector does not change an existing paid subscription or grant access. Public amounts and plan limits remain EUR 15/49 and the existing limits. Browser fixtures verify the selector only; they are not installed-app or hosted payment evidence.

## Controlled production native acceptance

A debug build can pin a fresh UUID through compile-time `GYRO_CLOUD_V2_NATIVE_ACCEPTANCE_SCOPE`. Its real production refresh credential uses a separate `production-acceptance` Keychain account scoped to that UUID; it cannot address the normal `production-v2` entry. Malformed or nil UUIDs leave that debug adapter unavailable. This input and factory are absent from release builds and cannot be supplied by a webview. The controlled bundle must also use a distinct bundle identity, persistent private data directory and launcher that restores that exact environment after Finder reopen. A data directory alone still does not isolate Keychain. The test uses the same production coordinator/Auth/transport/Keychain implementation, with explicit sign-in/restore and no startup authentication. Do not claim production acceptance from construction or unit tests.
