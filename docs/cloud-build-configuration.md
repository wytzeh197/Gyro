Normal builds expose Account, Plan & billing and Cloud through one native `cloud_connection` coordinator. No local `.app` launcher or `GYRO_CLOUD_ENABLED` override is required. Local/BYO work remains account-free.

No provisioning, data migration or deployment is implied by this file.

After separately approved production provisioning, copy only the reviewed public pins (API/share origins, production Auth project reference and publishable key, verified isolation flag and replacement staging project reference) into this file, commit them, and rebuild normally with `pnpm desktop:bundle`. No runtime endpoint input is accepted from a webview. Compile-time `GYRO_CLOUD_V2_*` pins remain available for explicit builds; a partial or mixed pin set fails closed. The active staging project is rejected by production adapters; the existing project remains reserved until the isolation gate is verified. Debug-only `GYRO_CLOUD_V2_STAGING_*` configuration uses separate native state and Keychain identities and is absent from release adapters.

Access credentials remain in native memory. Remembered refresh credentials use macOS Keychain under `dev.gyro.cloud.refresh`, separated by environment/project. Restoring a remembered session is explicit; startup never signs in or requests an email. Subscribe is the only path that can create a service account. Refresh rotates the refresh credential, rechecks the service snapshot and updates every account/billing/Cloud surface. Sign out fences older responses, clears native state/Keychain and attempts server plus issuer revocation; pending revocation is reported rather than silently treated as success. A verified Auth session alone never grants a subscription or allowance.

The legacy `gyro_cloud` in-memory login and staging API are no longer registered as installed-app commands. Historic previews are not production acceptance. Production restart, refresh, sign-out and fulfillment still need hosted end-to-end acceptance after deployment; local transport and native unit tests do not close that gate.

Use the [installed native Cloud acceptance checklist](releases/v0.1.0-native-cloud-acceptance.md) for the remaining authentication, Keychain, restart, refresh, revocation and paid-fulfillment gates. Preparing or running a local mock does not authorize email delivery, hosted mutations, charges or paid provider requests. A test data directory alone does not isolate the production Keychain entry; the checklist requires a separately controlled test user or an explicitly reviewed equivalent before remembered-session testing.

## Staging build during the project cutover

`config/cloud-staging.json` is the public staging build handoff. The staging builder reads this file instead of embedding a project reference in its source. After an approved staging move, replace it with the private service's reviewed `desktop-cloud-staging.public.json` export and update the reviewed replacement reference in `config/cloud-production.json`. Neither file contains credentials. Do not copy the production pins into the staging file.

Run `node scripts/build-cloud-staging-app.mjs` to build the separate debug-only staging app. It validates the public inputs before invoking build tools and uses `Cargo.lock` with `--locked`. Once production isolation is verified, stale staging pins that still point at the repurposed production project are rejected. Staging API/share origins must also remain separate from the configured production origins. The existing staging project stays usable while production remains disabled and the cutover has not occurred.

`pnpm test:cloud` includes offline checks for missing/mixed pins, secret-key rejection, nonpublic origins and the replacement-project boundary. These checks do not provision staging or establish hosted acceptance. The standard sidebar still has no Cloud destination; Account and Cloud remain accessible through Settings.
